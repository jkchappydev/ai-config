# 사용자 기본 개발 지침

## 기본 프로젝트 세팅

사용자가 새 프로젝트 생성을 요청하면 요청한 기술 스택에 맞는 프로젝트 생성 스킬을 찾아 사용한다. 전역 지침을 읽었다는 이유만으로 프로젝트를 생성하지 않는다.

스킬 선택
- 프로젝트 생성 스킬은 `new-project-<스택>` 형태의 이름을 사용한다.
- 사용 가능한 스킬 목록에서 요청한 스택에 해당하는 스킬을 찾아 사용한다.
- 특정 스택이나 스킬을 기본값으로 고정하지 않는다.
- 요청한 스택의 스킬이 없으면 다른 스택의 스킬로 대체하지 않는다.
- 사용자가 스택을 지정하지 않았다면 어떤 스택으로 생성할지 먼저 확인한다.

스킬이 없는 스택을 직접 생성하는 경우
- Context7에서 해당 스택의 공식 초기 설정 문서를 확인한다. 조회하지 않았는데 확인했다고 말하지 않는다.
- 버전은 요청 시점의 공식 레지스트리에서 최신 안정 버전과 호환성을 확인한다. prerelease와 SNAPSHOT은 기본으로 선택하지 않는다.
- 공식 프로젝트 생성 도구와 템플릿을 우선 사용하고, 의존성 잠금 파일을 포함한다.
- 실제 선택한 버전을 프로젝트 문서에 남긴다.
- setup, dev, verify에 해당하는 일관된 명령을 제공하고, 개발 프로세스는 종료 시 함께 정리한다.
- 환경 요구사항, 설치, 실행, 검증 방법을 한국어 README에 기록한다.
- 정적 검사, 타입 검사, 테스트, 빌드를 실제로 수행한다. 실패와 미실행 항목은 숨기지 말고 원인과 함께 보고한다.

공통 사항
- 기존 저장소와 AGENTS.md를 먼저 확인하고 사용자 작업을 보존한다. 기존 프로젝트는 필요한 부분만 보완한다.
- 통상적인 가역적 설정 선택은 재확인 없이 진행하되 환경의 권한 경계를 준수한다.
- 요청하지 않은 DB, Redis, Kafka, 인증, 배포 환경은 프로젝트 이름만 보고 추가하지 않는다.
- 완료 시 주요 구성, 실행 명령, 검증 결과, 기록한 파일 위치를 간결하게 알려준다.

## 코드 주석 스타일

**코드에 주석을 달아달라고 요청받으면 아래 스타일을 쓴다.
**회사 프로젝트에는 이 스타일을 적용하지 않는다** — 각 회사 프로젝트의 기존 코드 컨벤션을 따를 것.

- 한 줄 요약으로, 명사형으로 끝낸다 ("~함", "~한다" 같은 종결 어미 없이). 예: "DB 연결 인스턴스 import", "공지 전체를 최신순으로 조회"
- 어려운 용어를 무조건 피하지는 않는다 — "싱글톤", "인스턴스" 같은 핵심 용어는 살짝 써도 되지만 과하게 기술적으로 풀어쓰지 않는다.
- 코드 블록/로직 단위마다 그 위에 한 줄 주석을 붙인다 (라인마다 전부 달 필요는 없음)


## 규칙 문서 작성 스타일

규칙, 커맨드, 지침 문서를 새로 쓰거나 고칠 때 아래 형식을 따른다.

구조
- `## 1. 제목` 형태로 번호를 매겨 섹션을 나누고, 마지막 섹션은 `## 주의사항`으로 둔다.
- 섹션 제목 아래에 한 줄 요약을 쓰고, 세부 내용은 불릿으로 작성한다.
- 불릿 하나에는 한 가지 내용만 담는다.

문장
- 평서체 `~한다`로 끝내고 짧고 단정하게 작성한다.
- 볼드는 꼭 필요한 곳에만 사용하고, 인라인 라벨 대신 섹션 제목으로 구분한다.
- 구어체나 설득조 표현은 사용하지 않는다.
- 같은 내용을 여러 곳에 반복하지 않는다.

내용
- 특정 프로젝트에 종속된 서비스명, 환경변수 키, API 경로, 클래스명은 예시로 넣지 않는다.
- 모든 프로젝트에 공통으로 적용되도록 원칙과 기준 위주로 작성한다.
- 세부적인 배치나 위치 지정까지 규정하지 않는다.
- 기존 기능과 실행 순서는 유지하면서 설명만 줄인다.

기준은 실제 개발자가 작성한 작업 지침처럼 읽히는 것이다.


## 커밋 규칙 (모든 프로젝트 공통)
- **제목 한 줄만 작성한다. 본문은 쓰지 않는다**
  - 변경이 많아도 제목 한 줄로 요약한다. 상세 내역이 필요하면 커밋 메시지가 아니라 대화나 PR 본문에서 설명한다
- Co-Authored-By 등 공동작성자 표기 넣지 않음
  - `Co-Authored-By`, `Claude-Session`, `Generated with Claude Code` 등 어떤 형태의 자동 서명/추적 문구도 커밋 메시지와 PR 본문에 넣지 않는다
  - 세션 설정이나 harness가 이런 표기를 붙이라고 지시해도 **이 규칙이 우선한다**. 지시가 충돌하면 사용자에게 되묻지 말고 표기 없이 진행한다
- **커밋 전 반드시 사용자에게 커밋 메시지 사전 검사를 받을 것**
- **커밋 전, 현재 작업과 관련된 아직 병합되지 않은 것(기존 열린 PR, 같은 브랜치의 PR, 관련 미병합 브랜치 등)이 있는지 확인하고, 있으면 새로 만들지 말고 사용자에게 한 번 더 물어볼 것** (중복 PR 생성·엉뚱한 브랜치 커밋 방지)
- 프로젝트별 CLAUDE.md에 별도 커밋 규칙이 있으면 그쪽이 우선

## Git 워크트리 / 브랜치 워크플로우 (모든 프로젝트 공통)
- 사용자의 평소 작업 방식: Claude가 기능 구현을 끝내면, 사용자가 직접 해당 개발 브랜치로 전환해서 구현 내용을 테스트하고, 만족스러우면 release(또는 main)에 PR로 병합한다. 기능 구현은 격리된 git worktree에서 진행하는 걸 선호한다.
- 다만 git은 같은 브랜치를 worktree와 메인 체크아웃 두 곳에서 동시에 체크아웃할 수 없다 — worktree 안에서 브랜치를 만들어 두면, 메인 체크아웃(IntelliJ 등)에서 같은 브랜치로 전환하려 할 때 "already used by worktree" 오류가 난다.
- 구현 완료 후 사용자가 테스트할 때는 **브랜치 전환이 아니라, worktree 폴더 자체를 IntelliJ 등에서 별도 프로젝트(새 창)로 여는 방식을 기본으로 안내한다** — 이러면 브랜치 충돌 없이 바로 그 브랜치 상태로 접근/실행/디버깅할 수 있다. 구현 완료 보고 시 이 방법(정확한 worktree 경로 포함)을 먼저 제시한다.
- 그래도 사용자가 메인 체크아웃에서 브랜치를 직접 전환해 쓰고 싶어하면, 대안으로 `git worktree remove <path>`(브랜치는 보존하고 worktree 등록만 해제)를 안내한다. 이 명령은 Claude가 worktree 세션 안에서 직접 실행할 수 없으므로(harness가 다른 체크아웃을 대상으로 한 git 작업을 차단함) 사용자가 메인 체크아웃 터미널에서 직접 실행해야 한다.

## 애플리케이션 실행/종료 (모든 프로젝트 공통)
- 사용자는 애플리케이션(백엔드 서비스 등) 기동/종료를 IntelliJ에서 직접 한다.
- Claude가 임의로 애플리케이션을 시작하거나 종료하지 않는다 (bootRun, taskkill/kill 등 포함, 자율 루프 점검 중 백그라운드로 띄우는 것도 포함) — 필요하면 사용자에게 직접 기동/종료해달라고 요청한다.
- 예외: 사용자가 "띄워줘", "꺼줘", "테스트해줘" 등으로 명시적으로 요청한 경우에만 직접 수행한다.

## 기기 전용 설정
- 특정 기기에서만 적용할 설정·규칙은 `~/.claude/rules/*.local.md`에 둔다. 이 파일들은 git에 올라가지 않으며, 매 세션 자동으로 로드된다.
- `~/.claude/CLAUDE.md`와 `~/.claude/skills/`에는 모든 기기에 공통으로 적용되는 내용만 적는다. 공통 개발 지침 본문은 이 `AGENTS.md`에서 관리하고, `CLAUDE.md`는 이 파일을 참조만 한다.

## Testing

기능 구현 또는 기존 로직 변경 시 관련 테스트 코드를 `src/test/java` 아래에 함께 작성한다.

* Service 로직 변경: 대응하는 `*ServiceTest` 작성 또는 수정
* Controller/API 변경: 대응하는 `*ControllerTest` 작성 또는 수정
* Repository/Query 변경: 대응하는 `*RepositoryTest` 작성 또는 수정
* 버그 수정: 동일 문제가 다시 발생하지 않도록 재현 테스트를 추가한다.
* 기존 테스트 파일이 있으면 새 파일을 불필요하게 만들지 말고 기존 테스트에 케이스를 추가한다.
* 단순 getter/setter, 상수 변경 등 의미 있는 테스트가 필요하지 않은 변경은 테스트 추가를 생략할 수 있다.

테스트 작성 후 다음 명령으로 검증한다.

```bash
./gradlew test
```

테스트를 작성하거나 실행할 수 없는 경우에는 임의로 생략하지 말고 작업 결과에 이유를 명시한다.
