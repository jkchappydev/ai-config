# 흐름 그림 규칙 (모든 프로젝트 공통)

사용자가 "흐름 그림으로 그려줘", "그림으로 표현해줘"처럼 동작 흐름을 그림으로 요청하면 아래 형식을 따른다.

## 핵심 원칙
- **상자 아래 = 그 상자 안에서 일어나는 일** (읽는 값, 비교, 교체)
- **화살표 아래 = 상자 사이의 흐름** (무엇을 담아 어디로 전송/전달하는지, 왜 호출하는지)
- 처음 보는 사람이 상자와 화살표만 따라가도 흐름을 이해할 수 있어야 한다. 내용은 코드를 확인해서 쓴다.
- **디자인은 hallmark 스킬(`~/.claude/skills/hallmark`)의 Cobalt 테마(modern-minimal)** 기준으로 한다. 상세는 `references/themes/cobalt.md`.
  - 색은 모두 OKLCH 토큰으로 정의하고 토큰으로만 참조한다(hex 직접 사용 금지). 라이트 전용으로 고정(`color-scheme: light`).
  - 캔버스: 차가운 흰 바탕(`oklch(98.5% 0.004 250)`), 순백·순흑 금지. 맨 위 제목은 Space Grotesk 600, 아래 1px 헤어라인
  - 글꼴: 제목·상자 제목 Space Grotesk, 본문 Inter, 키·라벨·클래스명·헤더 예시 JetBrains Mono. 라벨은 고정폭 대문자 + 0.06em 자간
  - 상자: 채우기 없이 1px 헤어라인 테두리, 반경 10px. 그림자·옅은 색 배경·두꺼운 색 테두리 금지. 핵심 상자 하나(gateway)만 코발트 테두리
  - 신호색은 **코발트 하나**(`oklch(58% 0.20 256)`), 화면의 5% 미만. 상자 안 동작 설명 글자에만 쓴다
  - 화살표: 잉크색 1.5px 실선. 단계 번호(`1.` `2.` …)는 고정폭 굵은 잉크색
  - 헤더 예시: 그래파이트(어두운) 코드 카드, 밝은 고정폭 글자, 바뀌는 값만 밝은 코발트. 가짜 창 막대(점 3개) 금지
  - 실패: 빨강(위험) 토큰 1.25px 점선 + `불일치` 글자 + 빨간 1px 테두리 `403 반환` 상자
  - 기울임 제목, 그라데이션, 강조 막대, 점선 강조 박스 금지

## 구성
- **그림 한 장만** 만든다. 설명 문단, 단계 목록, 표, 범례, 그림 캡션은 넣지 않는다.
- 페이지 제목 외의 텍스트는 그림 안에만 둔다.
- 기본 배치는 왼쪽 → 오른쪽 한 줄이다. 흐름에 꼭 필요한 상자만 그린다.
- **게이트웨이를 거쳐 서비스끼리 호출하는 흐름**은 세로 지그재그로 그린다:
  ```
  [API 요청] → [호출 서비스 (login)] ─┐
                    ▲                ▼
                    │           [gateway] ─ 불일치 → [403]
                    │                │
               [받는 서비스 (user)] ◀─┘ ─ 불일치 → [403]
  ```
  - 호출 서비스와 받는 서비스는 같은 열에 위아래로, gateway는 그 사이 오른쪽에 둔다.
  - 호출 → gateway: 호출 서비스 오른쪽에서 나와 꺾여 gateway 위로 들어간다. 설명과 헤더 예시는 세로 구간 오른쪽.
  - gateway → 받는 서비스: gateway 아래 설명 밑에서 나와 꺾여 받는 서비스 오른쪽으로 들어간다. 설명과 헤더 예시는 세로 구간 **오른쪽(연결선 바깥)**.
  - 상자의 아래 설명(그 상자에서 일어나는 일)은 연결선들이 둘러싼 **안쪽 공간**에 둔다. 예: user 설명(`user/.env 의` / `INTERNAL_GATEWAY_TOKEN 과 비교`)은 user 상자 아래가 아니라 user 상자 위, 응답 직선 오른쪽에 왼쪽 정렬.
  - 꺾인 연결선의 **화살표 설명(단계 번호, 헤더 예시)은 바깥쪽**, 그 연결선이 시작되는 **상자의 아래 설명은 안쪽**에 둔다. 예: gateway → user 선은 gateway 아래에서 바로 출발하고, gateway 아래 설명(`INTERNAL_TOKEN_LOGIN 과 비교해서` / `일치하면 ~ 교체`)은 세로 선 왼쪽(안쪽)에 오른쪽 정렬, 3번 설명과 헤더 예시는 세로 선 오른쪽(바깥쪽).
  - 실패: 검증 상자 **오른쪽**에 빨간 점선 화살표(`불일치`)와 그 아래 `403 반환` 상자.
  - 응답: 받는 서비스 위에서 호출 서비스 아래로 **곧은 직선**. 설명은 직선 왼쪽, `일치 시`는 직선 시작점 옆. 호출 서비스의 아래 설명은 직선과 겹치지 않게 직선 오른쪽에 왼쪽 정렬로 적는다.
- 세로 화살표의 설명은 화살표 옆(왼쪽 또는 오른쪽)에 적는다. 세로 화살표가 상자 아래 가운데를 지나면 그 상자의 아래 설명은 화살표 옆으로 비켜 적는다.
- 사용자가 배치를 그려 주면 그 배치를 그대로 따른다.
- 화살표 아래 글자가 들어가도록 상자 사이 간격을 넓게 잡는다.

## 맨 앞 상자: API 요청
- 흐름을 시작하는 API 요청을 맨 앞 상자로 둔다.
- 상자 위 라벨은 `API 요청 (예시)`로 쓴다. 여러 요청에 공통인 흐름을 하나의 요청으로 예를 들어 보여 주기 때문이다.
- 상자 안에는 `POST /api/login/loginProc`처럼 메서드 + 경로와, 사용자가 실제로 하는 행동(예: `관리자가 로그인 화면에서 로그인`)을 적는다.
- 상자 아래: 그 요청을 누가 받는지(예: `login 서비스가 요청을 받음`)
- 이 상자에서 나가는 화살표 아래에 호출 이유를 적는다(예: `관리자 정보 조회를 위해` / `login → user 내부 API 호출`).
- API 요청 상자에는 클래스 이름을 적지 않는다.

## 상자
- 상자는 **서비스 단위**로 그린다. 한 서비스 안의 여러 클래스(예: 인터셉터 → 컨트롤러)는 상자 하나로 합친다.
- 클래스명은 각 상자 **최하단에 작게**(고정폭, 흐린 색, 11px) 한 줄에 하나씩 처리 순서대로 적는다(예: user 상자 `InternalTokenInterceptor` / `InternalAdminController`). 상자 제목·설명·상자 밖 설명에는 클래스명을 쓰지 않는다.
- 상자 위에는 아무것도 적지 않는다(폴더 경로 라벨 없음). 상자 안에 서비스 이름(예: `login 서비스`)과 한 줄 설명을 적는다. 단, 맨 앞 API 요청 상자의 `API 요청 (예시)` 라벨은 유지한다.
  - 예: `login 서비스` / `관리자 계정 조회 API 호출`
  - 예: `gateway 서비스` / `gateway/.env 값과 비교`
  - 예: `user 서비스` / `토큰 비교 후 관리자 계정 조회`
- 설정 파일(`.env`, `application-*.yaml`) 이름과 키 이름은 그대로 남긴다.

## 상자 아래 설명 (그 상자에서 일어나는 일)
- **두 줄 이내**로 적는다.
- 화살표 설명(기본 글자색)과 구분되도록 **글자만 해당 서비스 색**(초록/파랑)으로 칠한다. 배경 박스, 점선 테두리, 연결 점선, 왼쪽 강조 막대 같은 꾸밈은 넣지 않는다(AI가 만든 티가 나고, 박스 폭이 글자와 안 맞으면 빈 여백이 생긴다).
- 값은 **키 이름**으로 쓰고 고정폭 글꼴로 쓴다. 파일 경로는 상자 안 설명에 없을 때만 앞줄에 붙인다.
  - login: `login/.env 의` / `INTERNAL_CLIENT_TOKEN 읽음` (전송은 화살표 아래에 쓰므로 상자 아래에서는 반복하지 않는다)
  - gateway: `INTERNAL_TOKEN_LOGIN 과 비교해서` / `일치하면 INTERNAL_GATEWAY_TOKEN 으로 교체` (`→` 같은 기호 대신 조건을 말로 쓴다)
  - user: `user/.env 의` / `INTERNAL_GATEWAY_TOKEN 과 비교`

## 화살표 아래 설명 (상자 사이 흐름)
- 화살표 바로 아래 가운데에 **두 줄 이내**로 적는다. 화살표 위에는 글자를 넣지 않는다.
- **어떤 값을 어디에 담아 무슨 요청을 보내는지** 한 문장으로 쓰고, 길면 두 줄로 나눈다. 무엇을 어디에 담는지가 빠진 `~ 담아` / `~ 로 전송` 같은 표현은 쓰지 않는다.
  - login → gateway: `INTERNAL_CLIENT_TOKEN 을` / `헤더에 담아 관리자 계정 조회 요청`
  - gateway → user: `INTERNAL_GATEWAY_TOKEN 을` / `헤더에 담아 같은 요청을 user 로 전달` (일치 조건은 gateway 상자 아래 `일치하면 ~ 교체`에 이미 있으므로 반복하지 않는다)
- 값을 전달하지 않는 성공 화살표(예: 검증 통과 후 응답이 돌아가는 화살표의 시작 구간)에는 `일치 시` 한 마디만 적는다. 뻔한 설명은 붙이지 않는다.

- 값을 전달하는 화살표에는 설명 아래에 **헤더 예시 상자**(옅은 배경, 점선 테두리, 고정폭 글꼴)를 붙인다. 흐름에 관련된 커스텀 헤더(`X-...`) 줄만 넣는다(예: `X-Internal-Client: login` / `X-Internal-Token: Xq9fA2…`). 캡션, 메서드·경로, 본문은 넣지 않는다. 토큰 값은 실제 키가 아닌 가짜 예시 값으로 쓰고 `…`로 줄인다. 다음 구간에서 바뀌는 값만 굵게 표시한다.

## 성공/실패 분기와 최종 결과
- 최종 결과는 받는 서비스 상자 안 설명에 함께 적는다(예: `토큰 비교 후 관리자 계정 조회`). 같은 서비스 안의 결과를 위해 상자를 따로 만들지 않는다.
- 검증하는 상자는 **분기로** 그린다. 성공은 실선 화살표로 이어지고, 실패는 상자 아래 설명 밑에서 점선 화살표(`불일치`)로 아래로 내려 실패 상자로 끝낸다. 실패 상자에는 결과(예: `403 반환`)만 한 줄로 적고 부가 설명은 넣지 않는다.
- 실패 결과를 상자 아래 설명에 한 줄로 끼워 넣지 않는다.
- **응답이 돌아가는 화살표**도 그린다. 받는 서비스 상자 오른쪽에서 나와(`일치 시`) 그림 맨 아래(실패 상자보다 아래)를 지나, 응답을 실제로 받는 서비스 상자(호출한 쪽, 예: login 서비스) 왼쪽까지 꺾은선으로 잇는다. 아래에 무엇이 돌아오는지와 그 뒤 일어나는 일을 두 줄로 적는다(예: `관리자 계정(아이디·비밀번호) 응답 → login 으로 돌아옴` / `login 이 비밀번호 확인 후 로그인 결과 응답`). 돌아가는 곳은 코드에서 확인한 실제 호출자로 한다.

## 가독성
- 그림 폭(viewBox)은 1500 안팎으로 잡아 화면에 맞춰 줄어들어도 글자가 작아지지 않게 한다.
- 글자 크기(과하게 키우지 않는다): 그림 제목 22px, 상자 제목 17px 굵게, 설명 14px, 라벨 12.5px, 클래스명 11.5px(흐린 고정폭), 헤더 예시 12.5px 고정폭. 페이지 최대 폭은 viewBox 폭과 비슷하게 잡아 1:1에 가깝게 보이게 한다.
- 키 이름(`INTERNAL_...`)만 고정폭 + 약간 굵게 하고, 나머지 설명은 보통 굵기로 쓴다. 굵은 글씨는 `403 반환`, 응답 화살표 첫 줄, 바뀌는 헤더 값처럼 꼭 필요한 곳에만 쓴다.
- 설명 글자는 상자, 화살표, 다른 설명과 겹치거나 맞닿지 않게 충분히 띄운다. 세로 화살표 설명은 빈 쪽(왼쪽/오른쪽)에 둔다.
- **촘촘하게 그리지 않는다.** 상자 사이 가로 간격은 250px 이상, 세로 간격은 170px 이상 두고, 상자 안 글자와 테두리 사이도 20px 이상 띄운다. 상자 안에서 가장 긴 줄(예: `POST /api/login/loginProc`)이 테두리에 닿지 않게 상자 폭을 잡는다. 그림 폭은 1500 안팎이다.

## 기타
- 실제 비밀값(토큰, 비밀번호)은 앞자리라도 그림에 넣지 않는다. 키 이름만 쓴다.
- 결과물은 Artifact(HTML 인라인 SVG)로 만들고, 라이트/다크 테마를 모두 지원한다.
- 사용자가 더 넣으라고 하기 전에는 위 범위를 넘는 내용을 추가하지 않는다.
